## 镜像选择
### Windows Server
你真的要选这玩意吗？不开源，完完全全是黑箱子，性能要求还高，工具命令什么的和别的也不兼容，总之我是不用。你自己要选自己学学吧。
### Linux
#### Debian
非常老套成熟稳定的发行版。我一直在服务器上使用Debian，命令简单好学，教程足够多。不过Debian的更新策略注定了有些工具只能下载到过时的版本，而且默认Debian不支持非自由软件。
#### Ubuntu
Ubuntu是Debian系发行版的一个分支，Debian依靠社区维持更新，而Ubuntu依靠商业公司。虽然说这两个发行版根本上是发源于的关系，但是在细节上差别还是蛮大的，而且就算是桌面环境，基于Debian和基于Ubuntu也是基本不同的两个方向。Ubuntu Server LTS（长期支持版本）的支持时间比Debian LTS更长，发布时间更稳定，但是无论怎么说都不如Red Hat系列。不过Debian或者Ubuntu算是一个较为稳定的舒适圈吧，太舒适了导致我现在还没有转向RH系列。Ubuntu的软件库更加新，但是据说稳定性不如Debian，而且Ubuntu母公司Canonical在业界风评很差，有兴趣可以自己查一查wiki，总之不建议在任何场景下使用Ubuntu,除非你真的知道自己在做什么。
#### CentOS
古老的已经过时的发行版。不过CentOS Stream是 RHEL（Red Hat Enterprise Linux） 的滚动测试版，稳定性相对较差。
#### Fedora
Linux kernel创始人Linus Torvalds都在使用的优秀发行版。不过，Fedora属于Red Hat的上游滚动测试版本，一般情况下不适合在生产环境使用。生产环境更看重稳定性，每一个改动都有高昂的成本，更别提实时测试消耗的性能一般服务器根本承担不了，遇到并发场景直接歇菜。
#### 其他RH系发行版
比如Rocky Linux和AlmaLinux：LTS策略较为激进（比如支持十年），本身极其适合服务器使用，但是资料相较于其他发行版可能有些少，大胆部署，小心投产。
#### Arch
btw, I use Arch. 尽管Arch有着相当多优秀的特性，相当适合普通用户使用，但是由于是滚动更新，并不适合生产环境使用。
#### 国产发行版
比如Alibaba Cloud Linux、Anolis OS、openEuler和UOS。不推荐使用。鬼知道会出现什么兼容性问题，你搜不到资料的。
### BSDs
BSD系列和Linux同样属于类Unix系统，大体上与Linux差不多，不过很多细节与Linux不同，如果你有比较强的信息搜集能力，可以在尝试过Linux之后玩一玩。至于生态问题，很多命令行工具会提供BSD版本，一般软件即便不提供BSD版本也可以自行编译，不算简单但是也没有难如登天，毕竟BSD连Minecraft服务器都能部署呢。
### 版本问题
最好保持更新，防止某个漏洞干穿服务器，如果不想破坏性更新，可以进行热补丁更新。
## 预装应用
### Linux面板
**别选宝塔面板！别选宝塔面板！别选宝塔面板！别选宝塔面板！别选宝塔面板！**
最好是不要选择面板这种畸形产物，如果你愿意的话挑一个别的也不是不可以，但我不推荐任何一个，理由是面板缺乏命令化和高掌控度的操作，对新手来说处处都是坑，而且难以溯源。
对于有经验的人来说，使用面板监控服务器状态和一键自动化之类的很方便，但是仅限有经验。
### 容器与语言环境
基本都没必要预装。容器比如Docker，官网有一键安装的方法；各种环境比如Java、Go、Node.js之类的完全可以自己手动装，以保证自己对环境的掌控。什么你说你不会Linux？Why don't you learn it.
至于什么LAMP和LNMP之类的，你就当没看见。Apache、MySQL、PHP（WordPress）等等都是老掉牙的技术，完全不建议在新项目中使用。
## 计费模式
服务器的租金可以大体上看作长租和按量租两种。长租一般适合优惠产品，比如一年99的优惠机；而按量租一般是有明确的需求时使用的，价格相较于长租高还是低得看造化，比如你的用途、服务商的卑劣程度、你与服务商斗智斗勇的经验等。
另外流量的单独付费我建议按量付费，毕竟个人网页有人访问那真是谢天谢地了。至于需要做防止恶意刷流量之类的保护，这个交给Cloudflare吧。
## 架构
x86？arm？GPU？你如果感觉自己好像什么都不知道，闭眼选x86。如果你知道，那么应该不用我来推荐。
## 磁盘相关（备份与快照）
磁盘速度可能会成为程序的速度瓶颈。但如果真的出现这种问题，你应该先问问自己数据结构怎么写的而不是盲目增加硬盘速度。我选择最低速度，因为便宜。
备份与快照一般是收费的。如果是普通的个人网站，可以选择自行备份网页项目和部署流程文档，虽然比不上快照易用，但是可以省钱。
如果要自行备份，建议是在一开始就写文档记录下来用到了什么软件、修改了什么配置，然后使用tar命令打包，用scp命令下载。比如可以备份nginx配置文件、dist目录、PM2配置文件、ssh公钥、ssh配置文件、更新配置文件等等等等。
## 网络与安全组
IPv4端口，22对应SSH连接，3389对应Windows Server的远程桌面（一般标注为RDP），一般开启（其实一般很难用得到Windows远程连接，可以关闭）；80对应HTTP，安全性上需要打个问号，但部署较为容易，可以先打开再视情况关闭；443对应HTTPS，大多数情况需要开启。打开尽量少的端口，尽可能提高服务器的安全性。
至于邮箱、数据库、框架所默认占有的端口，不必在购买服务器时操作。
## 管理设置
### 密钥对与密码
* 密钥对：通过非对称加密算法生成一对密钥，包含公钥和私钥，在此处公钥部署在服务器上，面向全世界公开，而你持有唯一、不可再次下获取、不公开的私钥，在ssh登录时进行匹配认证。此处建议在服务商的控制台创建密钥对，并将其和你的服务器绑定。私钥不要上传到服务器或是发送给别人。接下来的内容默认使用密钥对登录。
* 密码：服务器保存账号和单向加密过的密码，此密码无法再解密，每次登录都会把输入的密码明文用同样的算法加密一次后和服务器上的进行比对。
* 密钥对通常情况下更加安全，也更方便，但是密钥对未必适合所有场景。往往使用密码可以快速为多个用户提供登录方式，而密钥对如果处处传播则会大大影响安全性。也就是说，密码建立在对"人"的信任上，而密钥对建立在对"设备"的信任上。
* 无论是用户名+加密密码比对，还是用户名+公钥私钥认证，都免不了会因为某个人的行为而泄漏密码或者私钥，而产生重大的安全问题。对一般用户来说，手里根本没有管理员权限，泄露什么也不会引发大乱子，而拥有管理员账号的人则需要视作定时炸弹。对ssh登录来说，密钥对登录是依托于本地的私钥文件的，传播管理员登录权靠传播私钥文件；至于密码登录显然是靠传播密码。可能你会产生疑问，难道这不都是一句聊天记录的事吗？是这样没错，可是密码可以被猜中或者暴力碰撞，密钥对不能。而且密码便于传播，私钥文件的传播没有那么方便，手机也可以传播。再一个，密钥对登录需要"一台有私钥文件的电脑"，设备在权限在；而密码登录可以是任意的电脑，人在权限在。所以选择密钥对登录往往稍微安全一点，但是仍然不如拥有TOTP认证的权限管理。至于TOTP，Github+Authenticator的绑定移动设备认证就是其中一种，感兴趣可以自己查一查，推荐所有新项目都使用TOTP认证。
### 用户组与用户权限
在权限管理上，Windows和Linux有着相似的逻辑。
Windows和Linux都存在"用户组"和"用户"的概念，并且都是通过判断用户所属的用户组来判断权限（极其简单地讲）。
对Windows来说，往往你所操控的就是某一个用户，需要更高权限的操作，就需要提升权限，或者更换更高级的用户。
在Linux上可以同时有多个不同用户组的自定义用户同时操作，权限控制较为直观明了，同时也有Windows一样的平时权限较低，需要时再提权的模式（不如说一般都是这样，分离的多用户才是相对少的）。
但是对于生产环境下的服务器，你可能需要分发多个普通用户甚至管理员账号给别人，或者有些操作仅能通过普通用户而不是管理员才能进行，这时候就需要多用户了。
所以建议服务器的"登录名"选择root，在进入系统之后再进行自定义。
## 其他默认项与选填项
基本建议是挨个看看，有需要自定义命名的可以自己起个好名字，其他的看不懂可以放过它们，因为大概率你不需要它们，也很少会有人全都精通每个名词的含义。
